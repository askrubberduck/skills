# askrubberduck

[English](README.md) · [Русский](README.ru.md)

**Навыки для агента, который доказывает, что сделал.**

Для Claude Code, Codex, Cursor, Copilot и других агентов с поддержкой Agent Skills.

Метод резиновой утки работает, потому что утка молчит. Объясняешь ей ошибку строка за строкой —
и примерно на четвёртой сам слышишь, где ошибся.

У твоего агента утки нет. Когда он говорит «готово», кто проверил?

Эти навыки и есть утка. Объясни цель. Покажи путь. Запусти проверку. Утка спросит, на чём
сломается твой вывод. И нужно ли было вообще это строить.

Любимое решение проходит те же проверки, что остальные. Решение самой утки — тоже.

## Скажи утке

Установи один раз и говори с агентом как обычно. По описаниям он выберет нужный навык.

Спрашивай на своём языке; описания навыков остаются английскими.
Записанных результатов выбора навыков для конкретных агентов и моделей пока нет — смотри [проверки языков](evals/README.md).

| Ты говоришь | Что получишь |
|---|---|
| «Возьми задачу в работу целиком» | `duck-run`: проверит цель, спланирует, сделает, попробует сломать. До согласованного финиша; локально значит локально. |
| «Почему это сломалось?» | `duck-why`: причину с доказательствами или оставшиеся гипотезы. Место для исправления найдено; писать его ещё не начали. |
| «Докажи, что цель или план обоснованы» | `duck-proof`: что могло бы их опровергнуть, что проверили и что устояло. Любимчикам скидок нет. |
| «Разбери и упрости этот механизм» | `duck-shape`: разберёт устройство, сохранит контракты и соберёт путь, для которого меньше нужно помнить. Затем проверит. |
| «Сделай независимое ревью» | `duck-review`: один вердикт, имена ревьюеров и доказательства за каждым замечанием. За участие не награждают. |
| «Попробуй сломать реализацию» | `duck-break`: выполненные атаки, входные данные и результаты. Представить сбой — ещё не получить его. |
| «Убери лишнее из комментариев и описаний изменений» | `duck-dry`: текст, который заслужил своё место, и проверки, что уборка не поменяла код. |
| «Подрежь бэклог» | `duck-cut`: уберёт устаревшее, объединит дубли, разблокирует нужное. Каждая задача должна заслужить своё место. |
| «Что дальше по задачам?» | `duck-scan`: что готово, что заблокировано и почему. Посмотреть можно бесплатно. |
| «Устрой гонку моделей» | `duck-race`: две независимые попытки, одинаковые проверки результата и победитель, который заслужил победу. |
| «Разнеси решение целиком» | `duck-roast`: замечания, выдержавшие проверку, действия по ним и конец раунда. |

## Установка

Агенты читают навыки при запуске. После установки любым способом начни новую сессию.

### Claude Code

```
/plugin marketplace add askrubberduck/skills
/plugin install askrubberduck@askrubberduck
```

Или из терминала:

```bash
claude plugin marketplace add askrubberduck/skills
claude plugin install askrubberduck@askrubberduck --yes
```

Можно связать клон с личным каталогом навыков — тогда имена будут без префикса плагина:

```bash
git clone https://github.com/askrubberduck/skills askrubberduck-skills
mkdir -p ~/.claude/skills
ln -s "$PWD"/askrubberduck-skills/skills/* ~/.claude/skills/
```

**Облачные сессии.** Claude Code в браузере, `claude --cloud` и routines получают свежий клон
репозитория и не читают `~/.claude/`. В этом репозитории всё уже настроено: ссылки в
`.claude/skills/` ведут на навыки, поэтому `/duck-cut` доступен из текущей ветки. В другом
репозитории объяви плагин в `.claude/settings.json`, чтобы он устанавливался при запуске сессии.
Плагины, включённые только в личных настройках, в облако не переезжают:

```json
{
  "extraKnownMarketplaces": {
    "askrubberduck": { "source": { "source": "github", "repo": "askrubberduck/skills" } }
  },
  "enabledPlugins": { "askrubberduck@askrubberduck": true }
}
```

### Codex

```bash
codex plugin marketplace add askrubberduck/skills
codex plugin add askrubberduck@askrubberduck
```

`master` меняется. Чтобы закрепить выпуск, добавь `--ref <tag>` к первой команде.

### Cursor, Copilot, Codex IDE и другие агенты с поддержкой Agent Skills

Свяжи клон с общим каталогом навыков:

```bash
git clone https://github.com/askrubberduck/skills askrubberduck-skills
mkdir -p ~/.agents/skills
ln -s "$PWD"/askrubberduck-skills/skills/* ~/.agents/skills/
```

`npx skills add askrubberduck/skills` делает то же через CLI `skills` и выбирает каталог
для нужного агента. Если агент читает `AGENTS.md`, но сам не находит навыки, вставь туда
[AGENTS-CATALOG.md](AGENTS-CATALOG.md).

Не добавляй отдельные ссылки туда, где уже установлен плагин: каждый навык появится дважды.

### Что написать для вызова

| Способ установки | Что написать |
|---|---|
| Плагин Claude Code | `/askrubberduck:duck-run` |
| Плагин Codex | `$askrubberduck:duck-run` |
| Отдельные ссылки, любой агент | `/duck-run`, `$duck-run` или выбрать навык в интерфейсе агента |

Внутри навыков соседний навык называется просто `duck-proof`: это имя работает
во всех способах установки.

## Знакомься со стаей

| Навык | Что делает |
|---|---|
| `duck-break` | Пробует сломать заявленное поведение системы и показывает, что случилось на самом деле |
| `duck-campaign` | Разбивает большую цель на независимые потоки работ, которые не ждут друг друга |
| `duck-cut` | Уменьшает бэклог по делу — убирает устаревшее, объединяет дубли, разблокирует нужное |
| `duck-decide` | Проводит владельца по решениям, которые тот откладывает, по одному за раз |
| `duck-diet` | Сажает контекст, память и расход токенов на диету, сохраняя необходимые инструкции |
| `duck-dry` | Сушит комментарии, docstring, сообщения коммитов и описания PR до неочевидных решений, контрактов и ловушек |
| `duck-frame` | Определяет устройство системы до планирования — «архитектуру решим потом» обычно значит «никогда» |
| `duck-land` | Вливает одобренную работу, обновляет записи проекта и убирает ветку и worktree; после посадки хвостов не остаётся |
| `duck-learn` | Превращает факты из сессий и результатов работы в уроки, чтобы за одну ошибку платить лишь однажды |
| `duck-plan` | Находит дыру в плане до начала стройки; предположения и приёмочные проверки должны выдержать критику |
| `duck-proof` | Заставляет цель, путь и результат заслужить доверие контрпримерами и выполненными проверками |
| `duck-race` | Даёт одну задачу двум семействам моделей с независимыми подходами; результат выбирают выполненные проверки |
| `duck-review` | Проводит одно независимое ревью другой моделью и выдаёт обоснованный APPROVE, REJECT или NOTE; за участие не награждают |
| `duck-roast` | Разбирает решение целиком, пока не проявятся слабые утверждения; замечание должно заслужить место, а раунд — закончиться |
| `duck-run` | Проверяет цель, строит план, делает и доказывает результат; локально значит локально |
| `duck-scan` | Находит готовое, заблокированное и оставшееся, ничего не меняя; посмотреть можно бесплатно |
| `duck-shape` | Разбирает механизм и собирает простейший надёжный путь, чтобы читателю меньше пришлось держать в голове |
| `duck-sweep` | Убирает отслужившие ветки, worktree, рабочие копии, временные каталоги и правила игнорирования; пруд остаётся чистым |
| `duck-why` | Находит причину сбоя до написания исправления, потому что симптом ещё не диагноз |

## На чём стоит утка

**Утка просит доказательства.** «Тесты зелёные» — начало разговора. Какие тесты? По чьим
требованиям? Каким вводом это можно сломать? После последней правки запускали? Проверка допуска
возвращает `APPROVE`, `REJECT` или `NOTE` с фактами, которые можно перепроверить.
Уверенность не считается.

**Утка не таскает лишнего.** У каждого факта одно место, у каждого правила один хозяин.
Если ради слоя приходится открыть ещё три файла, пусть объяснит, зачем он нужен.
Комментарий, пересказывающий следующую строку, уходит. Нужная граница остаётся,
как бы ни хотелось похвастаться числом удалённых строк. Короче ещё не значит понятнее.

**Утка сначала читает.** Пройди от входных данных до результата. Прочитай вызывающий код.
Выясни, какое ограничение породило некрасивое место, прежде чем его вырезать. Пока причина —
гипотеза, так её и называй. Дважды рассказанная история не становится воспроизводимым сбоем.

**Утка знает, когда хватит.** Агент ведёт работу и цикл ревью. Ты решаешь, когда меняются
цель, границы задачи или правила. Закрытый вопрос открывают новые факты. Желание ещё одного
ревьюера добавить абстракцию — не новый факт. Финиш не передвигают, когда до него добежали.

## Как утка ведёт задачу

`duck-run` ведёт работу. Каждый этап передаёт следующему то, что можно проверить.

1. **Разобраться**, `duck-frame`. Какой результат потеряем, если ничего не выпускать? Что уже
   решает задачу? Примени `duck-shape` при выборе границ, пока плохой стык не попал в план.
2. **Спланировать**, `duck-plan`. Сначала устройство работы, потом деление на части.
   Назови предположения и проверки, которые могут их опровергнуть. Дешёвый опыт — до дорогой догадки.
3. **Сделать.** Получи осмысленную падающую проверку, добейся её прохождения, затем примени
   `duck-shape` и `duck-dry` в пределах этого изменения. «Потом упростим» уже давали шанс.
4. **Доказать**, `duck-proof`. Проверь цель, поведение и итоговое устройство. Где нужно,
   `duck-break` проведёт враждебные эксперименты. Исправил — запусти затронутые проверки снова.
   Вчерашний зелёный не покрывает сегодняшнюю правку.
5. **Отдать на ревью**, `duck-review`. Когда этого требует задача или политика выпуска,
   независимые ревьюеры проверяют именно готовый кандидат. Нет ревьюера — нет ревью, а не тихое одобрение.
6. **Влить и убрать**, `duck-land`. Если ты разрешил слияние: влить, проверить результат,
   записать его и убрать остатки. Просил локальные изменения? Проверенный локальный diff и есть финиш.

До начала помогают `duck-scan`, `duck-cut`, `duck-decide` и `duck-campaign`;
по ходу — `duck-diet`; после — `duck-sweep` и `duck-learn`.

## Сколько уток проверяют твою работу?

Столько, чтобы проверить утверждение. Дополнительный стул не делает опыт убедительнее.

Для узкого доказательства может хватить одной решающей проверки. Для плана — одного
независимого критика. Для гонки нужны две изолированные попытки; в пинг-понге чередуются
падающая проверка и исправление. Выбирай способ, способный вскрыть ошибку, и заранее задай
предел. Агент подберёт разумный состав, если ты не указал свой. Комитет настраивать не надо.

Для выпуска порог строже: обычно один ревьюер из подтверждённо другого семейства моделей;
для изменений безопасности, приватности, данных или правил допуска — два ревьюера разных
семейств, хотя бы один не из семейства автора. Твои явные условия и политика репозитория
имеют приоритет. Маленький разбор не заменяет обязательную проверку. Нет участника — порог
не становится ниже. Подробности — в [правилах проверки](skills/duck-review/references/challenge.md).

Передача репозитория другому поставщику требует твоего разрешения. Если оно уже покрывает
эту работу, утка помнит. Спрашивать снова — не дополнительная забота.

Доказательства должны лежать там, где их найдут. Отдельную проверку можно описать прямо
в ответе. При передаче работы следующему этапу используй существующую запись проекта:
кандидат, выполненные проверки и открытые вопросы. Proof и break могут делить одну страницу.
Куча квитанций ещё не куча доказательств.

### Как утка ограничивает раунды ревью

Координирующий агент сохраняет согласованные цель, ограничения и проверки во всех раундах.
Ревьюер может найти новый дефект относительно этих условий. Превратить свежее пожелание
в новое требование — не может. У замечания сохраняются причина и доказательство закрытия;
новая формулировка не открывает его заново.

Отказ возвращает к причине: `duck-why`, если она скрыта; разбор постановки, если неверны
исходные предпосылки; планирование, если не сработало разбиение; гонка или пинг-понг, если метод
снова пропускает тот же класс ошибок. Перед третьим раундом агент объясняет, какие новые факты тот даст.

По умолчанию — три раунда ревью всего. Смена ревьюера или названия проблемы не обнуляет счётчик.
На пределе агент прекращает рассылать работу, сохраняет кандидат и незакрытые замечания,
оставляет выпуск без одобрения. Другой предел задаёшь ты или правила репозитория.
Нельзя гоняться за единогласием бесконечно. Нельзя одобрить, потому что все устали.

Пока тебя нет, агент продолжает техническую работу в рамках задачи и удерживает только то,
для чего нужен твой ответ. Молчание не выбирает новую цель.

## Как утка доказывает свою работу

Каждый push запускает `scripts/validate-distribution.py --self-test`: манифесты читаются,
ссылки ведут на навыки и ресурсы, сгенерированные файлы совпадают с исходниками,
намеренные поломки обнаруживаются.

Это доказывает целостность пакета. Чтобы проверить саму работу утки, дай ей задачу, где
согласиться было бы ошибкой, зелёный тест прячет дефект или ревьюер двигает финиш.
Смотри, что она сделала. [Сценарии поведения](evals/proof-cases.md) описывают проверки
и проведённые опыты. Непроведённый опыт остаётся непроведённым даже в README самой утки.

Версии и изменения — на [странице выпусков](https://github.com/askrubberduck/skills/releases).
