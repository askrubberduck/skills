# Duck Campaign

Turn the requested outcomes into manageable workstreams, and carry each to its authorized
endpoint. Split work when separate execution, ownership or release helps. Two separately shippable
small changes are not by themselves two packets.

Follow the user's language unless they ask otherwise. Keep commands, paths, identifiers,
quoted errors and machine-readable verdicts unchanged; the duck asks for evidence in any language.
Before a step that requires the procedure of a skill, load that skill. Follow its named section
within existing authority. A conditional or routing mention needs no load until it applies.

Carry existing authority through the campaign. Local work ends with verified local changes.
Commits, PRs, pushes and merges require their own authorization. A planning-only request ends with
the plan. Keep unresolved decisions attached to their dependent work.

## Establish the work that is needed

Use [`duck-scan`](../duck-scan/SKILL.md) to locate current work, and read relevant product
constraints and source. Reuse existing records and decisions. Delegate bounded read-only
investigation only when it helps.

Apply [`duck-cut`](../duck-cut/SKILL.md)'s existence check to the proposed work items: what
required outcome is missing, what satisfies it, and which findings share a cause? Remove
speculative or superseded work. Recheck a work item that grows. Do not quietly expand the owner's
goal.

Before dependent plans, use [`duck-frame`](../duck-frame/SKILL.md) to settle shared contracts and
consequential unknowns. Reuse valid design decisions instead of a fresh frame per packet. Keep the
campaign's shared contracts in its existing work record. Create one only if no adequate home
exists. An owner decision blocks only its dependent work. Continue other settled,
authorized work, even before the roster has packets.

## Group by execution needs

Keep related changes together if they share a rule, verification path or small delivery surface.
Repeated findings at one boundary get one repair with several cases. Separate work with different
owners, release schedules, material risks or truly independent execution. Do not overlap ownership
of concurrently edited files.

Each packet names its outcome, affected scope, dependencies and completion check, and has an
independently verifiable finish, not only a named code area. Use the existing work-item convention.
A small campaign can need only one record with several units, not one directory, branch, design and
plan per checklist item.

Plan substantial or uncertain packets with [`duck-plan`](../duck-plan/SKILL.md). A small settled
unit can keep its steps and checks in the campaign record, as [`duck-run`](../duck-run/SKILL.md)
permits. Preserve repository-required independent input, and record actual
participation. Solo work is not an independent challenge.

## Execute and keep the roster current

Use [`duck-run`](../duck-run/SKILL.md) for execution and verification. Pass it the outcome, valid
shared decisions and remaining authority. Parallelize only independent work that benefits from it.
Isolate concurrent writers or destructive checks as that skill requires. Apply
[`duck-diet`](../duck-diet/SKILL.md) to keep dispatch overhead proportionate. Send every packet
review through [`duck-review`](../duck-review/SKILL.md), never a reviewer CLI run by hand. Its
ledger, round bound, loop diagnosis and outage parking exist only there.

Maintain one roster in the durable work record: packet, state, dependencies, evidence and next
action, plus branch or worktree if used. Finish a ready unit and continue to the next without
another go-ahead. Do not open a new packet while another waits on review or integration this run
can finish first. Reconcile concurrent changes, and verify the combined result before completion.

Before a turn ends while work runs, say in one line what runs and what each item waits
on. In that line, name the event for the next update, and about when. On each completion,
give one roster line. Shut a worker down once its packet lands or returns. Flag an idle worker with
uncommitted changes.

Count each worker message once. A status notice older than your last instruction to that worker is
a repeat. A cut-off report counts only after its tail arrives. Brief each worker so a replacement
can start from the brief alone: worktree, base, candidate identity, findings with evidence paths,
gates and rules. Ask that reports lead with gates and unsettled items.

If blocked, record the actual blocker and a concrete next action, and continue independent work.
Do not invent consent, rescope away a required outcome or retry an unchanged failure indefinitely.
Contrary execution evidence, or an owner correction of a result, reopens the affected shared
design before dependent work continues. Stop when the authorized work is complete or all remaining
work is blocked, and state which. A "complete" on a broad request lists what it left out and why.

At a context boundary, preserve the roster, candidate identities and valid evidence. A scheduled
continuation needs a supported authorized mechanism and a confirmed booking; a written next step is
not one. Use [`duck-sweep`](../duck-sweep/SKILL.md) for authorized cleanup:

- Inventory untracked and ignored files before removal.
- Preserve unknown files.
- Verify kept work at its durable home.

Do not delete work only to empty the roster.
